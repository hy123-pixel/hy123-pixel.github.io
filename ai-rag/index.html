RAG 不是魔法：检索增强生成的工程实践

让模型回答“它真正知道的内容”，关键在于把检索链路做好，而不是盲目换一个更大的模型。

工程实践难度：中等

先把问题拆开

知识库问答失败时，很多人第一反应是修改 Prompt。实际上，一个答案需要经过“问题理解 → 文档召回 → 片段重排 → 上下文拼装 → 模型生成”五个环节。任何一个环节出错，最后看起来都像是模型在胡说。

一条可靠的检索链路

  1. 切分：优先按标题、段落和语义切分，保留文档名、章节、更新时间等来源信息。
  2. 召回：向量检索负责语义相似，关键词检索负责精确命中；混合召回通常比单一方式更稳。
  3. 重排：用更精细的模型对候选片段重新排序，避免把相似但不相关的内容塞进上下文。
  4. 生成：要求模型只依据上下文回答，并在答案中带出引用片段或文档来源。
经验：“召回了什么”往往比“模型多大”更影响知识库问答的最终质量。

切分不是越细越好

切得太细，片段失去语境；切得太大，又会浪费上下文窗口。一个比较实用的起点是按标题分组，再以 300～800 字作为软限制，并给相邻片段留少量重叠。最终仍须用真实问题来验证，而不是迷信某个固定数字。

给答案加上证据

Prompt 可以明确三条规则：上下文没有答案时直接说“不确定”；每个结论尽量对应来源；不要把推测写成事实。程序侧再检查引用是否存在、答案是否超出权限范围，才能让系统真正可用。

用数据而不是感觉评估

准备一组真实问题，分别观察召回命中率、答案忠实度和回答完整度。每次调整切分大小、Top-K 或提示词，都应该用这组问题回归。RAG 是一条数据管道，不是一个开关。

先让证据可靠，再让表达自然。一个可解释的普通答案，通常比一个漂亮但无法追溯的答案更有价值。

RAG 的核心不在模型多大，而在你能否把答案锚定到自己的资料：切分、召回、重排与引用每少一环，模型就越容易凭空编造。把检索链路做扎实，模型才真正成为你知识的延伸，而不是又一个会自信胡说的对话框。
