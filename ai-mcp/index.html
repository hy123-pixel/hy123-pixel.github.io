MCP 是什么：给 AI 一套标准化工具接口

如果工具调用解决“AI 如何做事”，MCP 解决的就是“AI 如何用统一方式认识和连接这些工具”。

先理解它解决的混乱

在没有统一协议时，每个 AI 客户端都要为每个数据库、文件系统和 SaaS 服务单独写一套适配器。工具越多，维护成本越高，权限、参数和返回结果也很难保持一致。

MCP（Model Context Protocol）把外部能力抽象成资源、提示模板和工具。客户端负责发现和调用，服务端负责暴露能力，双方通过结构化消息交流。

MODEL CONTEXT PROTOCOL
AI 客户端⇄MCP Server⇄文件 / 数据库 / API
一次接入，多个 AI 客户端可以复用同一套工具能力

一个 MCP Server 应该包含什么

  1. 工具：可以被模型调用的动作，例如查询订单、搜索文档。
  2. 资源：可以被读取的上下文，例如文件、表结构、项目说明。
  3. 提示模板：将常见任务封装成可复用的工作提示。

安全边界比接入速度更重要

不要因为“接上了 MCP”就让模型拥有全部权限。服务端应该按用户身份限制数据范围，对写入、删除、发消息等副作用操作增加确认，并保留完整调用日志。

实践建议：先做只读 MCP Server，例如文档搜索和项目知识库；确认权限、超时和错误返回稳定后，再开放写操作。

MCP 与普通 API 的关系

MCP 不是要替代所有 API，而是为 AI 客户端提供一层更适合发现、描述和调用工具的统一接口。已有 API 可以包装成 MCP 工具，业务服务仍然负责真正的权限和数据校验。

MCP 的价值不是增加一个新名词，而是让 AI 工具生态从“每个客户端单独适配”变成“能力可以被发现和复用”。

真正发挥 MCP 的作用，不在于马上接入最多的工具，而是先想清楚哪些能力值得被标准化暴露：从只读检索、知识库起步，再逐步开放带确认的写操作。当你把工具描述清楚、权限收紧、调用留痕，新的 AI 客户端就能直接复用同一套能力，而无须为每个应用重写适配器。
